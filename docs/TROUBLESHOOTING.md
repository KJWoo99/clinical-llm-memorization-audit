# 트러블슈팅. 실측으로 잡은 결함

정답 파서는 합성 예시가 아니라 실제 노트 4.5만 건(앞 20,000건과 전 구간 무작위 25,000건)으로 검증했고, 무작위
표본에서만 나온 결함이 있었음(5번).

## 1. 정답 출처가 애초에 틀림. `prescriptions` 는 퇴원약이 아님

- 증상: 기획은 `prescriptions` 테이블을 정답으로 쓰려 함. 한 입원 건을 대조하니 노트의 퇴원약은 8개인데 테이블의 퇴원
  시각 근처에는 12개가 있었음(헤파린 예방투여, 독감백신, 염화칼륨, 생리식염수 플러시가 더 있음)
- 원인: 그 테이블은 입원 중 투약 전체를 담음
- 수정: 정답은 노트의 `Discharge Medications` 절에서 파싱하고, 테이블은 약물 어휘 검증에만 씀

## 2. 비식별화가 괄호를 반만 지워 용량이 이름에 딸려옴

- 증상: `약이름 SR (제품명 ___ 15 mg PO Q8H` 꼴(구조만 옮긴 예시)에서 용량, 용법이 전부 약물명에 붙음
- 원인: 비식별화가 닫는 괄호까지 지움. 괄호 안은 이름으로 취급함
- 수정: 닫히지 않은 괄호가 남으면 그 앞에서 자름(`tests/test_notes.py` 의 `TestUnclosedParenthesis`)

## 3. 번호 목록에 복용약이 아닌 것이 섞여 있음

- 증상: 퇴원약 번호 목록에 보류된 약(`HELD- ...`), 외래검사 안내, 인슐린 규칙표, 의료용품(펜 니들, 혈당측정기 등)이 섞임
- 원인: 정답에 넣으면 올바르게 뺀 모델이 누락으로, 오답으로 두면 그대로 읽은 모델이 환각으로 깎임
- 수정: 정답에서 빼되 환각으로도 세지 않는 중립 항목으로 분리함(`TestItemClassification`)

## 4. 제형을 떼면 다른 약이 망가짐

- 증상: 용량이 없는 약은 제형이 이름에 붙음(`Multivitamin Tablet`). 제형을 떼기만 하면 이름이 바뀌는 약이 있음
- 수정: 원래 이름과 뗀 이름을 모두 별칭으로 인정함
- 비고: `Nicotine Patch` 처럼 제형이 이름의 일부인 경우는 patch 를 제형 목록에 넣지 않아 떼지 않음(`TestDosageFormAlias`)

## 5. 전 구간 무작위 표본에서만 나온 것 3건

1, 2 는 앞 20,000건에는 없고 무작위 25,000건에서 나옴.

1. 단수형 `needle` 이 용품 목록에 없어 `pen needle, diabetic` 이 약으로 남음. 용품 목록에 단수형을 넣음
2. 소문자 `sig` 를 못 잘라 `furosemide oral sig unknown` 이 이름으로 남음. 대소문자를 가리지 않게 고침
3. 시드를 고정해 다시 뽑은 무작위 25,000건에서 꼬리표 꼴이 아닌 `disp` 가 약물명에 남는 것이 3종(노트 3건)
   나옴. `Sig` 처럼 단어 경계에서 자르게 고침

- 결과: 고친 파서로 평가 표본 300건의 정답을 다시 만들어도 바뀐 항목은 없음(`tests/test_notes.py`)
- 함께 찾은 것: 희귀도 빈도 파일이 옛 파서로 센 값으로 남아 `glucose gel`(지금 파서로 노트 1,540건)이 빈도
  0 으로 읽힐 수 있었음. 표본은 두고 빈도만 다시 셈(`run_phase1_sample.py --frequency-only`, 91종 바뀜)
  - 그 노트는 audit 분할이라 희귀도 표와 채점 결과는 바뀌지 않음(`tests/test_audit_conditions.py`)

## 6. 감사 기준이 오탐을 냈고, 고쳤다고 적은 수정이 코드에 없었음

- 증상: "용법, 조제 지시문이 약물명에 섞였는가"를 부분문자열로 검사해 `rosiglitazone` 의 `sig`, `enema disposable` 의
  `disp` 를 결함으로 잡았음. 당시 약국 어휘 8,836종 중 5종이 오판돼 정상 데이터에서도 감사가 실패함
- 원인: 고쳤다고 적었지만 나중 점검에서 정규식에 단어 경계가 여전히 없었음. 주석과 문서만 고친 상태였음
- 수정: `\b` 로 실제로 고침
- 결과: 2만 노트의 결함은 1건(`lancet ... disp`, 단수형 `lancet` 누락)만 남음. 제형 표기(`multivitamin tablet`)는
  결함에서 분리함

## 6-b. 정답 파서가 실제 약을 의료용품으로 버리고 있었음

- 증상: 저혈당 치료제 `Glucose Gel`, `Glucose Tab` 이 정답에서 빠짐. 2만 노트에서 이 토큰 하나로 빠진 100건 중 93건이
  실제 약이었고, 모델이 맞혀도 환각으로 채점됨
- 원인: 용품 목록 `_SUPPLY_WORDS` 에 `glucose` 가 있었음
- 수정: 26개 토큰을 약국 어휘 8,836종과 대조해 `glucose`, `strip`, `kit`, `pump` 는 빼고, 혈당 측정 용품은
  `blood glucose` 구로만 잡도록 함
- 결과: 표본(300건)은 다시 뽑지 않고 정답 컬럼만 다시 만듦. 모델 입력 700행의 SHA-256 이 전후로 같아 추론은
  그대로 두고 채점만 다시 함

## 7. DUA. 집계 파일도 그냥 올리면 안 됨

- 증상: 약물 빈도표(`phase1_drug_frequency.json`)를 커밋했다가 되돌림
- 원인: 1회만 등장하는 약물이 1,786종이라 특정 노트와 연결될 여지가 있고, 원자료에서 10분이면 다시 만들 수 있음
- 함께 고친 것: 모델 응답 JSONL 도 노트에서 파생된 약물 목록이라 함께 막음

## 8. 감사 조건의 분모가 다른 노트였음

- 증상: 감사 조건은 audit 분할 100건에 걸려 있는데, "정상 대비 몇 %"의 분모로 main 분할 200건의 정상 점수를 쓰고
  있었음(두 분할의 교집합 0건). 발견 당시 사전등록 4모델의 두 분할 정상 F1 차이는 +0.004\~+0.090
- 수정: 같은 노트의 정상 점수로 나눔. 그 응답은 선택 단계에 이미 있어 재추론하지 않음
- 결과: 판정은 하나도 바뀌지 않았고 비율만 최대 6.6%p 움직임(Meditron3 셔플 73.4% -> 66.8%)
- 남은 한계: 이 분모는 변형 선택에 쓰인 점수라 위로 편향돼 있음(변형별 점수는 `phase3_selected_prompts.json` 의
  `by_variant`)

## 9. 사고하는 모델은 답을 내기 전에 생성 상한에 걸림

- 증상: Baichuan-M2 는 선택 단계 300건이 전부 `<think>` 도중 상한 512 에 잘렸고, 파서는 사고 조각에서 약 3개를 긁어
  채점하고 있었음(다른 모델은 9\~10개)
- 수정
  - 스위치가 있으면 사고를 끔(Baichuan-M2, Apertus 8B)
  - 없으면 상한을 늘림(HuatuoGPT-o1, MedReason 1536)
  - 스위치가 없는 II-Medical 8B 는 상한을 8192 로 올리고 그 62행만 다시 만듦. 4096 에서도 선택 단계 62건이 상한에
    닿았기 때문임(58건은 반복, 4건은 결론 직전의 긴 사고)
- 비고: 반복에 빠진 행은 형식 실패로 셈. 규칙은 prereg 부록에 먼저 적음

## 10. 사고 안의 초안을 최종 답으로 읽을 수 있었음

- 증상: HuatuoGPT-o1 의 사고 안에 "지금까지 목록: [...]" 같은 초안이 있어, 앞에서부터 배열을 찾는 파서가 초안을 채점할
  수 있었음
- 수정: 사고 시작 표시로 시작하는 응답은 마지막 끝 표시 뒤만 답으로 읽고, 끝 표시가 없으면 실패로 셈(`after_reasoning`
  으로 따로 집계)
- 함께 찾은 것: MedReason 의 끝 표시(`## Final Answer`)를 빠뜨렸던 것도 채점 전에 응답을 읽다 찾아 더함
- 확인: 응답 3,927건을 대조해 약 목록이 바뀐 행이 없음

## 11. 읽지 못한 배열을 "JSON 준수, 약 0개"로 세고 있었음

- 증상: Meditron3 8B 가 `[["Allopurinol", "___ mg Tablet"], ...]` 이나 `[{"valsartan": "40 mg"}]` 처럼 답한 행을
  `_coerce_list` 가 빈 목록으로 돌려주고 순수 JSON 성공으로 셈
- 수정: 원소가 있는데 하나도 못 읽으면 곧바로 실패로 바꿈. 뒤의 본문 배열 탐색으로 넘기면 두 번째 쌍을 약 목록으로 읽음
- 결과: 응답 3,169건에서 약 목록이 바뀐 행은 0, 경로 표시만 4건 바뀜
- 그대로 둔 것: OLMo-2 의 `{"약": "용량"}` 사전 답 25건은 원래대로 형식 위반으로 둠(결과를 본 뒤 파서를 넓히지 않음)

## 12. OLMo-2 MeditronFO 는 배포된 토크나이저가 기반 모델과 다름

- 증상: OLMo-2 32B 두 모델은 같은 노트도 입력 토큰 수가 평균 8.6% 다름
- 원인: MeditronFO 의 tokenizer.json 에 기반 모델의 사전 분할 정규식이 없어 같은 글이 다르게 쪼개짐(같은 팀의 다른 두
  MeditronFO 는 기반과 같음)
- 확인: 결과를 보기 전에 판정선을 정하고 기반 토크나이저로 한 번 더 돌림
  - 선택 단계: grounded 만 판정선을 넘음(0.7136 대 0.2587). 약이 있는 노트에도 `[]` 로 답하는 불안정성 때문이었음
  - 최종 단계(선택된 schema, 공통 133건): 두 토크나이저의 차이는 −0.0020(−0.0186 \~ +0.0127)으로 0 을 포함해 결론을
    바꾸지 않음
- 남은 한계: 배포 토크나이저는 문맥 4,096 초과로 최종 600행 중 140행(기반 토크나이저는 99행)을 잃음. 짝 비교는 두 모델
  모두 문맥 안인 노트로만 함

## 13. MedGemma 는 사고 스위치가 없는데 숨은 표시로 사고를 씀

- 증상: MedGemma 1.5 4B 는 템플릿에 사고 옵션이 없는데 응답 일부가 `<unused94>thought` 로 사고를 쓰고 `<unused95>`
  뒤에 답함(최종 minimal 600건 중 240건)
- 원인: 사고 규칙이 이 표시를 몰라, 잘린 사고 안의 초안을 약 13\~37개짜리 답으로 읽고 있었음
- 수정: 채점 전에 응답을 읽다 찾아 시작, 끝 표시에 넣음. 상한 512 는 그대로 두고 잘린 사고는 형식 실패로 셈
- 결과: 응답 12,939건 대조에서 MedGemma 만 바뀜. 선택 단계 점수가 바뀌어 변형이 schema(0.629)에서 minimal(0.653)로
  옮겨 가 최종 단계를 다시 만듦

## 14. 배치 크기가 섞인 파일 하나가 프롬프트 선택을 뒤집음

- 증상: 이어받기로 Gemma 3 27B 두 모델의 선택 단계 파일에 배치 2 행 24개와 배치 1 행 276개가 섞임
- 원인: 배치가 다르면 bf16 덧셈 순서가 바뀌어 greedy 출력이 갈릴 수 있음(배치 등가성 검사에서 16건 중 II-Medical 8B
  8건 등)
- 수정: 24행을 배치 1 로 다시 만듦. 행마다 배치 크기를 기록함
- 결과(당시): 상위 두 변형의 차이가 0.001 미만이던 두 모델의 선택이 뒤집혀 규칙대로 최종 단계를 다시 만듦
- 지금: Gemma 3 27B minimal 0.9430, MeditronFO grounded 0.9422 로 선택은 같고 최종 점수는 두 모델 모두 0.923
- 남은 한계: F1 만 보는 규칙이라 준수율이 낮은 변형(Gemma 3 27B minimal 78%, MeditronFO minimal 29%)이 뽑힐 수 있음

## 15. 실행이 중간에 끊김. 이어받은 파일은 지우고 처음부터 다시 만듦

- 증상: 추론 도중 서버가 여러 번 꺼져 실행이 중간에 끊김. 이어받기로 끝난 파일에 끊긴 시도가 쓴 행이 섞일 수 있었음
- 수정: 실행 기록의 시도 303건과 산출물 작성 시각을 대조해, 끊긴 시도가 행을 보탠 최종 파일 8개를 지우고 처음부터
  다시 만듦
- 확인: 남긴 파일은 `scripts/verify_reproducibility.py` 로 표본 322건을 원래 배치, 상한, 템플릿 인자로 다시 만들어 글자
  단위로 대조함. 불일치 0건
- 함께 찾은 것: Apertus 두 모델의 템플릿이 실행 당일 날짜를 넣음. 짝의 두 모델은 같은 날 돌아 짝 비교에는 영향이 없음

## 16. 채점기가 정답 쪽 중복만 그대로 두어 맞힐 수 없는 누락을 만들고 있었음

- 증상: 같은 약이 두 줄로 적힌 퇴원약(감량 요법 등)에서 약 이름만 쓰는 모델은 두 번째 항목을 맞힐 수 없었음. 표본의
  60개(정답 2,697개의 2.2%)라 16모델 모두 micro-F1 이 0.009\~0.013 씩 낮게 실림
- 원인: 채점기가 예측 쪽 중복만 합치고 정답 쪽은 그대로 둠
- 수정: 정답도 별칭 집합이 겹치면 합침(표본의 `n_gold` 는 층화에 쓰인 값이라 그대로)
- 함께 고친 것: 희귀도 계산이 별칭 목록과 이름 목록을 따로 훑어 엉뚱한 약을 세는 두 번째 결함(기존 표본에서는 실제로
  어긋난 적 없음)
- 결과: 짝 승패, 순위표, 암기, 구조 판정은 모두 같았고, 절제 8회차는 추론부터 다시 돌림

## 17. 별칭 규칙이 정답에만 걸리고 예측에는 걸리지 않았음

- 증상: 예측은 정규화한 문자열 하나로만 대조해 `Multivitamin Tablet`, `Lipitor (Atorvastatin)` 같은 답이 환각과
  누락으로 깎임. 같은 약을 제품명과 성분명으로 두 번 쓰면 두 번째가 환각이 됨(16모델 정상 조건 환각 3,114건 중 92건, 3.0%)
- 수정: 예측에도 같은 별칭 규칙을 적용함(`src/evaluate.py`)
- 결과
  - 선택 변형과 짝 승패, 유의 여부는 그대로임
  - 순위표에서는 Gemma 3 27B 두 모델, Apertus 8B 와 MedReason 8B 가 자리를 바꿨지만 둘 다 차이가 0.01 미만
  - 점수는 제형이나 괄호를 붙여 답하는 모델에서 오름(MedGemma 0.643 -> 0.660 등)
  - 판정이 바뀐 것은 Baichuan-M2 의 구조 판정 하나. 셔플 비율이 89.9% 에서 90.0% 로 올라 기준선을 넘음
